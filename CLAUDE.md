# EasyITP

ITP (vehicle inspection) station management app. One manager = one ITP station: ITP records, reminders for expiring ITPs (WhatsApp/SMS), appointments calendar, reports, CSV import/export. Admin manages manager accounts and sees aggregated numbers only. JWT auth.

## Stack
- Backend: Spring Boot 3.3.5, Java 17, Maven (`mvnw`), JPA + PostgreSQL, Spring Security + JWT, Lombok, commons-csv.
- Frontend (`frontend/`): React 19 + TypeScript, Vite, Tailwind 4, axios, react-router, MUI X Scheduler (calendar), Vitest.

## Layout
- `src/main/java/org/example/easyitp/` — `controller/`, `service/`, `repository/`, `entity/`, `dto/`, `security/` (JwtUtil, JwtRequestFilter, CurrentUser), `config/` (SecurityConfig incl. CORS, DataSeeder).
- `src/main/resources/application.properties` — config via env: `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`, `JWT_SECRET` (>= 32 bytes), `ADMIN_PASSWORD`, `ALLOWED_ORIGINS`, `SHOW_SQL`, `RESEND_API_KEY`, `MAIL_FROM`, `APP_URL`, `CRON_SECRET`, `ANTHROPIC_API_KEY`, `PORT` (default 8080). `JWT_SECRET`, `ADMIN_PASSWORD` (only for the first start on an empty DB) and `ALLOWED_ORIGINS` have no defaults: startup fails without them; local defaults live in `application-dev.properties` (profile `dev`, enabled by `./mvnw spring-boot:run`; for `java -jar` pass `--spring.profiles.active=dev` or the env vars). Default JVM time zone is Europe/Bucharest (`TimeZoneConfig` + `-Duser.timezone` in the Dockerfile).
- Schema: **Flyway** migrations in `src/main/resources/db/migration` (`V1__baseline.sql` = schema at the switch, skipped on existing DBs via `baseline-on-migrate` + `baseline-version=1`; `V2` drops Hibernate's enum CHECKs). Hibernate runs with `ddl-auto=validate`, so every entity change needs a new `Vn__description.sql` (never edit an applied migration; no enum CHECK constraints). Tests on H2 skip Flyway (`create-drop`); verify new migrations on a local Postgres (`docker run postgres:16`) both on a fresh DB and on an existing one.
- `frontend/src/` — `api/` (one module per backend controller, shared `axiosInstance.ts`), `components/` (pages + modals; pages are lazy-loaded in `App.tsx`), `context/` (`AuthContext.tsx` provider, `auth.ts` context + `useAuth`), `utils/` (pure helpers with `*.test.ts`), `types/index.ts`.
- Public booking page `/programare/:slug` (no login): backend `/api/public/**` is permitAll, rate-limited per IP (`BookingRateLimiter`) with a honeypot field; settings per station on `AppUser.booking*`. Capacity: each appointment has `vehicleCategory` + `durationMinutes` (legacy null = 30 min); per-station durations per vehicle type in `AppUser.bookingDurations` (`InspectionDurations`, defaults car 20 / 4x4 30 / van 45); online slots = the type's own grid plus the end times of other bookings, offered only if the whole interval fits on one of `bookingCapacity` lines.
- Daily digest email: GitHub Actions (`daily-digest.yml`) calls `POST /api/internal/daily-digest` with `X-Cron-Secret`; `DigestService` builds an HTML and a WhatsApp text version and claims the day atomically per manager (`AppUserRepository.claimDigest`, released on failure), so overlapping runs never send twice; each manager picks the channel: `EmailService` (Resend) or `WhatsAppService` (CallMeBot, free personal-use API, per-manager key never returned to the client). External HTTP calls have timeouts (`HttpTimeouts`); email retries once with a Resend `Idempotency-Key`, WhatsApp retries only when the connection failed. Never commit API keys.
- Registration scan: `POST /api/itp/scan-registration` (multipart `image`) sends the photo of the Romanian talon to Claude Haiku (`RegistrationScanService`, forced tool use, fields A/E/D.1/D.3/B/C.2.x), maps make/model through the car dictionary; the photo is never stored, 200 scans/user/day cap. Frontend shrinks the photo first (`utils/image.ts`). Talon only, never ID cards (GDPR).
- Fleets (B2B): a manager creates `Fleet`s (company, CUI, plates in `fleet_plates`) and one login per fleet (`AppUser` with role `FLEET` + `fleetId`). Manager API `/api/fleets/**`, fleet portal `/api/fleet-portal/**` (`FleetService`): vehicles matched by normalized plate against the station's latest ITPs, and a monthly statement (informative, not a fiscal invoice; CSV + printable page built in `utils/fleet.ts`). `SecurityConfig` limits FLEET to the portal and `/api/account/me|password`.
- Owner reports: inspectors are names only (`AppUser.inspectors`, `/api/account/inspectors`), picked per ITP (`ItpRecord.inspector`, last choice remembered per device). `ReportService` adds per-inspector monthly rows and retention (vehicles with an ITP last year that reached expiry: returned this year vs lost, with a call list). Admin gets neither names nor the lost-client list (aggregates only).
- Dark mode: `ThemeProvider` (`context/ThemeContext.tsx`, `useTheme` in `context/theme.ts`) sets `<html data-theme>`; an inline script in `index.html` applies it before paint. `index.css` remaps the slate scale via Tailwind CSS variables, maps `bg-white`/`.modal-panel` to `--surface`, and overrides colored tints per class (generated block). Don't add `dark:` classes everywhere; use `var(--surface)` / `var(--color-slate-*)` for inline colors, and the `dark:` variant only for one-off fixes. MUI calendar gets its own dark theme.
- Security: errors go through `config/ApiExceptionHandler` as `{"message"}` (bad dates/params/body and DB constraint errors -> 400); don't add per-controller handlers. JWT carries `tv` = `AppUser.tokenVersion`; `revokeTokens()` on password change/reset, deactivation and fleet password change (password change returns a new token). Login: emails lowercased + `findByEmailIgnoreCase`, failed attempts limited per email and per IP (`LoginRateLimiter`), dummy bcrypt for unknown emails. Client IP for limits = `CF-Connecting-IP` (`security/ClientIp`; Render is behind Cloudflare and keeps client-sent X-Forwarded-For). CSV cells go through `CsvCells.cell` (quoting + formula neutralizing). Admin report export has no plates/names. Frontend security headers + CSP in `frontend/vercel.json` (no inline scripts: the theme script is `public/theme-init.js`; `connect-src` must list the backend URL).
- Clients (B1): one `Client` (person) can own several `Vehicle`s. `ClientService.resolveOwner` decides the owner when an ITP is saved (form or CSV import): same name as the current owner -> keep; a station client with the same name (`ClientKeys.nameKey`, no diacritics/case) and phone (`clients.phone_key` = last 9 digits) -> that one; current owner has no other car -> rename; else a new client. Editing an ITP's plate moves only that ITP (to the car with the new plate, or a new car if the old one keeps other ITPs). Deleting an ITP/vehicle/client cleans up empty vehicles/clients and unlinks appointments (`ClientService.deleteRecords`). `ItpService.validate` checks the ITP form (400 with a Romanian message). Clients page `/clients` (`/api/clients/**`, MANAGER only): search, client file with cars + ITP history, edit client/car (plate collision -> 409), move a car, merge clients, possible duplicates (same phone or name), delete. V4 merged existing duplicate vehicles/clients.
- History (B2): `AuditService` writes `audit_events` (station `userId`, actor email, action CREATE/UPDATE/DELETE/RESTORE/MERGE/MOVE/IMPORT, entity ITP/CLIENT/VEHICLE, human summary, field-level `changes` "Label: old → new" per line). Log every user-visible change of ITPs/clients/vehicles; skip empty diffs. Deletes store a JSON snapshot (`ClientSnap` → vehicles → ITPs + linked appointment ids) and return the event id in the `X-Audit-Event` header (exposed via CORS); `HistoryService.undo` restores it within 30 days (reuses a car with the same plate, never duplicates an ITP, relinks appointments). Events older than a year are purged by the daily digest call. Frontend: deletes have no `confirm()`; they call `offerUndo` (`utils/undo.ts`) and the global `UndoToast` shows "Anulează" for 10 s; page `/history` (filters, restore button).
- Consent (C1, GDPR): `Client.reminderConsent` = GIVEN / DECLINED / null (unknown, legacy), with `consentAt`, `consentSource` and a personal `optOutToken`. The ITP form checkbox (`ItpFormDTO.reminderConsent`, null = don't touch) gives or withdraws consent via `ClientService.applyFormConsent` (unchecking never clears DECLINED); online booking stores it on `Appointment.reminderConsent` and it is prefilled into the ITP started from the appointment. DECLINED clients are filtered out of reminders (and so the daily digest); automatic sends (C2) must only go to GIVEN. Public STOP page `/stop/:token` (`/api/public/stop/{token}`), station toggle in the client file (`PUT /api/clients/{id}/consent`). Reminder messages get `{stop}` (appended on a new line when the template lacks it).
- Automatic SMS reminders (C2): per station `AppUser.autoSms*` (enabled, provider `SMS_GATE` = the station's Android phone via the "SMS Gateway for Android" cloud API `POST {smsgate.url}/3rdparty/v1/messages` with basic auth, or `SMSLINK` = `secure.smslink.ro/.../json.php` GET with connection_id/password; passwords write-only), stages in days (default 30,7) and an SMS template. `AutoReminderService.runDaily` runs inside the daily internal call: latest ITPs whose expiry falls in a stage window (stage .. stage-5 days), only consent GIVEN, mobile numbers, no NOT_INTERESTED/SCHEDULED status and no upcoming booked appointment for the plate; one `reminder_sends` row per (ITP, stage), FAILED retried up to 3 days, 300/station/day cap. `SmsText` renders without diacritics (GSM 160 chars) and appends the STOP link after rendering; `utils/smsText.ts` mirrors it for the preview. `SmsSender` never retries a request that may have left; custom SMS Gateway URLs must be https + domain (no SSRF). Settings card `AutoSmsCard` in Contul meu (`/api/account/auto-sms`, `/test`, `/log`).
- Landing page (`LandingPage.tsx` + `components/landing/*`): shown on `/` to visitors who are not logged in (`RootGate` in `App.tsx`); logged-in users get the app. Only real features and no invented numbers/testimonials; pricing says plans are being prepared. Gallery images in `frontend/public/landing/` are screenshots of a fictive demo station ("ITP Exemplu", made-up names). The ROI calculator (`utils/roi.ts`) is an estimate from the visitor's own inputs. "Cere o demonstrație" posts to `/api/public/leads` (honeypot, 3/hour per IP, `leads` table, optional email to `LEADS_EMAIL`); admin sees them at `/leads` (`/api/admin/leads`).
- Public pages share `PublicHeader`/`PublicFooter` (`components/landing/PublicChrome.tsx`; company data in `utils/company.ts`: VLN SOLUTIONS, CUI RO48267925). `/statii` lists stations for drivers (`GET /api/public/stations`: active managers with online booking on and `AppUser.publicListing` != false, toggle in the booking settings card). `/confidentialitate` and `/termeni` (`LegalPage.tsx`) are the legal texts; keep them in sync when adding processors (hosting, email, SMS, AI) or new personal data.
- Appointments without no-shows (C3): every appointment has a `manageToken`; the client's SMS link `/p/:token` (`/api/public/appointments/{token}`, `AppointmentSelfService`) shows it and allows cancel / move to another free slot (`BookingService.availableSlots(..., excludeId)`) until 60 min before; client actions are stored in `clientAction`/`clientActionAt` and shown in the calendar. `AppointmentSmsService` sends, on the station's SMS channel and only when enabled (`AppUser.apptConfirmSms` / `apptReminderSms`, in the SMS card): a confirmation right after an online booking (and after a move) and a reminder in the daily run for tomorrow (Saturday also covers Monday), once (`reminderSentAt`). These are transactional (no reminder consent needed). Status `NO_SHOW` ("Neprezentat") is set by the manager; reports show the appointment stats (no-show rate over concluded appointments).
- SMS included in the subscription: provider `PLATFORM` sends through the platform's SMSLink account (`SMSLINK_CONNECTION_ID` / `SMSLINK_PASSWORD`, env only, never in code or DB). Each station has `AppUser.smsPlan` (0/300/600/1000 SMS per month, set by the admin, `PUT /api/admin/managers/{id}/sms-plan`); `SmsQuotaService` counts billed parts per month in `sms_usage` (a >160-char text = 2) and `SmsSender` refuses past the plan. Prices (no VAT) in `utils/smsPlans.ts`: 129 / 219 / 349 RON. STOP links in SMS use the short path `/s/{token}` (`/stop/` still works).
- Other deadlines (C4): a `Vehicle` has optional `deadlines` (`vehicle_deadlines` element collection: `DeadlineKind` RCA / ROVINIETA / TAHOGRAF, `dueDate`, `contactedAt`), set from the ITP form (`ItpFormDTO.deadlines`, null = don't touch, a kind with null = clear) or the client file (`VehicleUpdateRequest.deadlines`); a new date clears `contactedAt`; changes are audited as VEHICLE updates and kept in delete snapshots. `DeadlineService`: "De contactat" view `/api/reminders/deadlines` (30 days ahead / 30 expired, PUT `/{vehicleId}/{kind}` {contacted}), form prefill `/api/itp/deadlines?plate=`. Optional automatic SMS (`AppUser.autoSmsDeadlines`, needs auto SMS on) 7 days before with a fixed text (`AutoReminderService.DEADLINE_TEMPLATE`), only consent GIVEN and not marked contacted; logged in `reminder_sends` with `vehicle_id`/`kind`/`due_date` (`itp_record_id` null).
- Data scoping: every manager query filters by `client.user.id`; legacy clients may have `user_id = null` and must be skipped.
- Same license plate (ignoring spaces/dashes/case, `PlateUtils`) = same vehicle; only the latest ITP per vehicle counts for expiry. The normalized plate is stored in `vehicles.normalized_plate` (set by `Vehicle` on save, indexed) and "latest" is computed in SQL (`ItpRecordRepository.LATEST`, a NOT EXISTS keyed on the normalized plate; keep the plate equality outside any OR or Postgres can't use the index). Don't load a whole station to filter in Java: use the targeted queries (`/api/itp/records` paged + search, `/summary`, `/history`, reminders window, GROUP BY stats for admin, date-ranged reports). `/api/itp/dashboard` (full list) is kept only for the CSV export and compatibility.

## Commands
- Backend: `./mvnw spring-boot:run` (profile `dev`) · build `./mvnw clean package` · test `./mvnw test` (H2 in-memory, profile `test`; no Postgres needed)
- Frontend (in `frontend/`): `npm run dev` (proxies `/api` → localhost:8080) · `npm run build` · `npm run lint` · `npm test`
- CI: `.github/workflows/ci.yml` runs backend tests + frontend lint/test/build on push.
- Docker: `Dockerfile` builds backend only (runs as non-root, `MaxRAMPercentage=75` for Render's 512 MB).
- Health: `/api/health` is DB-free (UptimeRobot keep-alive, lets Neon sleep); `/api/health/deep` also checks the DB. Frontend shows a "server is starting" banner when a normal request takes > 4 s (`utils/serverStatus.ts`, `ServerWakeBanner`).

## Deploy
- `main` auto-deploys: frontend on Vercel (`frontend/`, SPA rewrite in `vercel.json`), backend on Render (Dockerfile), DB on Neon.
